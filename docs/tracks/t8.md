## Sprint log

### T8.1 — IndexedDB, compare-and-swap saves, locks, autosave, snapshots, file format

Delivered `core/persist` (repository, autosave controller, locks, snapshots, migrations, file format, asset
store and GC) and `ui/library` (the session that wires them into the app, and the frozen `useAutosave` hook).
Persistence is **on** in the app: importing `useAutosave.ts` (the shell does, for the save chip) starts it in a
browser, replaces the shell's memory backend with the repository one, and the chip switches to "Saved".

`core/persist/folderClient.ts`, `backups.ts` are still Step 0 placeholders), the library UI (`StartScreen` is
still the Step 0 stub; only its copy changed, see Deviations 6), `state/slices/library.ts`, prefs persistence,

The backend: `create` = `repo.create` + `storage.persist()` (updates `capabilities.storagePersisted`); `open` =
`repo.open(id, 'edit')` (null for an unknown id); `leave` = flush, then release the lock — and if the changes are
still unsaved it **throws** (the shell then neither closes nor discards; the lock of the project it was about to
open is given back).

Banners (all through the shell's `showProjectBanner`): read-only "Open in another tab" + **Edit here instead** →
"Asking the other tab to hand over…" → (5 s) "The other tab isn't answering" + **Take over** / Ask again;
"Editing moved to another tab" / "Another tab took over this project" + Edit here instead; conflict copy
"Another tab saved a newer version of “…”" — "Your changes are safe in “… (copy, 14:05)”, which you are
editing now." + Open the original (new browser tab; it opens read-only there while another tab holds it);
"This tab was closed for an update" + Reload (+ Export a backup when changes could not be flushed); "Finishing an
update" (blocked); save failed "Not saved" + **Export a backup** (from memory: works while IndexedDB fails).

## Deviations from the spec, with reasons

1. **Persistence starts when `useAutosave.ts` is imported** (in a browser with IndexedDB), not from
   `projectSession.ts` as s0c request 1 suggests: `ui/shell` is S0-owned, and the shell's chip switches to
   `useAutosave` by itself the moment the hook is implemented (`saveStatus.ts`), so without the switch the chip
   would claim "Saved" (or "Saving…" forever) over a memory backend. Consequence: **`e2e/smoke.spec.ts:95`
   expects "Not saved yet" and now sees "Saved"** (5 card tests). With that one assertion changed to `'Saved'`
   the whole e2e suite passes (18/18, checked and reverted — `e2e/**` is integration-owned). See request 1.
2. **Take over bumps the stored rev** (and snapshots the document first). §5.5.2 says the old holder's later
   save "is caught by compare-and-swap"; without the bump, the old holder's FIRST save after a steal would
   succeed (same rev) and the taker's next save would become the copy instead. With the bump the outcome is
   deterministic: whatever the old holder still saves becomes a copy (the acceptance wording).
3. **"Edit here instead" protocol**: `release {id, from}` → the holder flushes (≤ 4 s), lets go, waits until the
   lock manager confirms, then posts `released {id, to}`; the asker retries `ifAvailable` every 100 ms until the
   5 s deadline (Chromium can report the release a moment after the message). A hand-over that arrives after the
   timeout still gives the asker the lock (`lock-acquired`): the user asked for it. The asker never queues a
   blocking lock request, because `LockManagerLike` has no `signal` to cancel one.
4. **`useAutosave().status` maps `unsaved` to `saving`** (s0b request 11): the chip says "Saving…" during the
   800 ms debounce.
5. **The conflict copy's original "reopens read-only beside it" via a banner action**: one tab holds one
   `projectStore`, so the original cannot be open next to the copy in the same tab. "Open the original" opens it
   in a new browser tab, where it is read-only while another tab holds it (tested).
6. **`StartScreen` copy** (still the Step 0 stub until T8.2): the empty state said "Saving isn't switched on yet…"
   and the restore button "Available once projects are saved" — both false now; changed to "Your projects are
   saved in this browser as you work." and "Coming soon: restore a project from the projects folder or a backup".
7. **A save never refuses a missing stored document** (deleted in another tab): it writes it again (rev =
   base + 1). Never losing the open tab's work wins over the deletion; a banner tells the user.
8. **A stored document of a newer format version is a conflict** for `save` (never overwritten) and `open`
   throws `MigrationError('newer-version')`.
9. **`remove(id)` deletes the document and its snapshots, never assets** (GC removes them after 7 days if
   nothing names them), and refuses a project another tab is editing (`ProjectLockedError`).
10. **Asset GC is global**, by reference, not by key prefix: conflict and imported copies share the original's
    keys (`<originalId>/<sha>`, s0b request 10), so a prefix says nothing about who uses an asset. References are
    every `<id>/<sha256>` string in every project and snapshot, followed through JSON assets (a model revision's
    `meshAssets`, s0b request 4). The delete transaction re-reads the references and deletes nothing that round
    if a document names a key the first pass did not see.
11. **Without `navigator.locks`** (an insecure context such as a LAN IP over http) the app uses an in-tab lock
    manager: compare-and-swap still prevents overwrites; only the read-only mode is missing there.
12. **`beforeunload`** asks only when changes cannot be saved (a failing save, storage closed); a pending save is
    flushed instead (the shell's guard is off for a repository backend).

## Ambiguities resolved

| Where | Reading |
|---|---|
| §5.5.3 "same id and identical content" | The documents compared by canonical JSON without `rev` and `updatedAt`, and every asset of the file already stored. |
| §5.5.3 import with the same id, other content | New id (`crypto.randomUUID`), name "<name> (imported YYYY-MM-DD)" (local date); its rev continues after every rev in the file so later autosave snapshots never collide with the imported ones; imported snapshots are re-keyed to the new id. |
| §5.5.3 import of an old format | Migrated; the original is stored as a snapshot "Before update to format N" and the migrated doc gets the next rev. |
| §5.5.2 "keep the last 30 plus one per day for 30 days" | Last 30 by rev; plus the newest snapshot of each local calendar day younger than 30 days. Pruned inside the save transaction whenever a snapshot is written. |
| §5.5.2 snapshot at a rev that already has one | Kept (same document); a named reason replaces the label "Autosave", never another name. |
| §5.5.2 "Request `navigator.storage.persist()` when the first project is created" | On every create (idempotent; `persisted()` is checked first). |
| §5.5.2 "doc and new assets in one transaction" | `projects`, `assets` and `revisions` in one readwrite transaction; a conflict writes nothing, not even the assets. |
| `ProjectRepository.saveAsCopy` "Takes the copy's lock" | With `ifAvailable` on the new id; the autosave then releases the original's lock and clears read-only. |
| Project ids | `crypto.randomUUID()` (s0b request 8). |

## Requests for integration

1. **`e2e/smoke.spec.ts:95`**: expect `'Saved'` instead of `'Not saved yet'` (persistence is on; Deviation 1).
   With that line changed the suite passes 18/18 in this worktree.
2. **S0 `ui/shell/ProjectName.tsx`**: the field ignores outside name changes while it has the focus (it keeps
   the focus after Enter). After a conflict copy (`rebind` renames the document to "… (copy, 14:05)") the field
   still shows the old name, and the next blur commits it — renaming the copy back to the original's name. No
   data is lost, but the two projects then share a name. Suggested: sync `text` from `name` when the document id
   changes or when `name` changes while the text equals the previous name.
3. **S0 `ui/shell/projectSession.ts`**: `openProject` opens the next project (taking its lock) before leaving the
   current one; when leaving fails (unsaved changes) T8's backend gives the lock back, but the order "leave, then
   open" would avoid taking it at all. Also the Workspace shows "This project isn't here" when `openProject`
   rejects for that reason; a toast with the message would be clearer.
4. **§5.5.2 wording**: say that Take over bumps the stored rev (Deviation 2) and describe the hand-over messages
   (Deviation 3); say how the original "reopens read-only beside it" (Deviation 5).
5. **§5.5.4 / T8.2**: the folder mirror's per-project `sync:<id>` meta entries live in the `meta` store created
   here; nothing writes it yet.
6. **Read-only tabs do not follow the editor's saves** (they show the document as it was when opened, and get the
   latest on Edit here instead / Take over). Live refresh would re-open the project (new session: derived results
   recomputed) on every save of the other tab; left for later unless the owner wants it.
7. **Long-lived tabs and GC**: an asset that an undo left unreferenced is deleted after 7 days; a redo after that in
   a tab that never closed re-names it — `save` reports it as missing and the autosave stores it again from the
   tab's cache, but not if `uncacheAssets` dropped it. Rare; a "deleted assets" grace list in `meta` would close it.

## How it was verified

- Unit tests (vitest; node environment, the hook under happy-dom), all on `fake-indexeddb` 6.2.5 and the Step 0
  fakes: `core/persist/__tests__/repo.test.ts`, `autosave.test.ts`, `pure.test.ts`,
  `ui/library/__tests__/persistence.test.ts`, `useAutosave.test.ts`. Property tests: migrations keep every leaf
  field of 500 random documents through a two-step chain (pure, deterministic; a lossy step is refused);
  `isValidProjectId` equals `isProjectId` on 2 004 random strings; SHA-256 and base64 against `node:crypto` /
  `Buffer`.
- Real browser (`e2e/tracks/t8-persist.spec.ts`, Chromium 1243, real IndexedDB, `navigator.locks`,
  `BroadcastChannel`): a project survives a reload and is listed; a second tab opens read-only and "Edit here
  instead" hands over after the holder's flush; a hung tab (15 s busy main thread) — Take over appears after
  ≥ 4.5 s (measured from the click) and takes the lock, and when the old tab wakes its unsaved edit becomes
  "… (copy, HH:MM)" with the conflict banner, while the original keeps the taker's version. No console errors.
  Chromium note: CDP `Page.setWebLifecycleState('frozen')` still delivers BroadcastChannel messages to the frozen
  page, so it does not model an unresponsive tab; the spec uses a busy main thread.
- Screenshots (light and dark, 1280 × 800) of every persistence banner: written by the spec to `CPG_T8_SHOTS`.
